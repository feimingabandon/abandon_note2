# Abandon Note 天气与每日宜忌方案调研

调研日期：2026-09-24。本文核对当前项目源码、厂商公开文档、开源库源码和许可证。价格与配额是访问当日信息；方案属于研究建议，尚未接入产品。

## 结论与选择

**天气建议优先评估和风天气，保留 Open-Meteo 作为可选来源；每日宜忌建议离线计算，独立于天气服务。** 如果必须同时满足无需注册、无需密钥、无需服务端，保留 Open-Meteo 更符合条件，但必须接受它的免费使用范围和服务保障限制。

每日宜忌有两条值得采用的免费路线：

- **接入便利优先：`lunar-javascript`。** JavaScript、无第三方依赖、MIT 许可，提供现成的 `getDayYi()`、`getDayJi()`。本次已做隔离功能验证。
- **规则出处与可解释性优先：`cnlunar-js`。** JavaScript/Node.js 移植库，当前版本 0.2.0、MIT 许可；上游 `cnlunar` 以《钦定协纪辨方书》的神煞与宜忌取舍规则为依据。需要先核对移植一致性和历法边界，再作为正式数据源。

结合你希望继续研究《梅花易数》《周易》等文献的方向，我更倾向于：**保留当前节假日体系，对 `cnlunar-js` 做候选验证；如果目标只是尽快展示传统黄历条目，`lunar-javascript` 是接入更直接的备选。** 不建议先接一个来历不明的免费黄历 HTTP 接口。

## 当前代码已经具备什么

当前天气实现位于 [weather-service.js](C:/addFile/idea/项目/abandon/abandon_note2/src/main/services/weather-service.js)。它具有地区选择、经纬度解析、请求超时、磁盘缓存、手动刷新限制、失败返回旧缓存等能力。中国地区并行请求 `cma_grapes_global` 与自动模型，再合并结果；其他地区使用自动模型。请求的日预报范围为 16 天。

这里有三项会影响实际体验：

1. **两个模型都经过 `api.open-meteo.com`。** 模型互补可以改善缺失字段、预报覆盖，但不能解决同一个域名不可达的问题。跨供应商故障回退才具有网络上的独立性。
2. **当前天气与逐日预报共用启动及每日 09:00 的刷新策略。** 如果展示“现在”的气温与天气，刷新间隔需要明显短于一天；否则用户觉得“不准”，可能首先是数据已经过时。
3. **`current` 不等于当地站点的直接实测。** Open-Meteo 文档说明当前天气基于 15 分钟天气模型数据。项目中的“当前实况”措辞应与真实数据口径核对。其逐日天气代码又表示一天中较严重的天气情况，与此刻天气本来就可能不同。[W1][W2]

当前历法实现位于 [calendar-metadata.js](C:/addFile/idea/项目/abandon/abandon_note2/src/main/calendar/calendar-metadata.js)，依赖 `chinese-days 1.5.9`，生成农历、节气、节日及法定休假信息。**宜忌不是现有数据中的字段。** 不需要为了增加宜忌而替换已经工作的调休与节日逻辑。

## 天气服务比较

| 方案 | 本次核实的免费条件 | 特点与限制 | 对本项目的判断 |
|---|---|---|---|
| Open-Meteo | 免费接口限非商业使用；600 次/分钟、5,000 次/小时、10,000 次/日、300,000 次/月；无需 API Key | 全球数值预报，当前已接入；免费接口无可用性保证；多变量、多模型、超过两周的数据可能按多个调用量计数 | 适合无需注册的默认来源或独立备选；不能称作无限免费 |
| 和风天气 QWeather | “天气和基础服务”价格分组每月前 50,000 次请求为 0 元，其后 950,000 次为 0.0007 元/次 | 涵盖天气、分钟预报、预警等；需要凭证及来源署名；分组内服务累计，不能按每种接口各有 5 万次计算 | 国内产品优先评估候选，但准确率须实际比较 |
| 心知天气 | 官方有永久免费个人版；覆盖国内 370 个主要城市、3 天预报，实况免费字段较少 | 覆盖和预报长度有限；免费版与 14 天试用版不同，商业使用条件需要按实际产品核实 | 可做轻量个人应用；不适合直接补齐当前区县及 16 天日历能力 |
| 彩云天气 | 公开计费文档列出按量、包月、企业套餐，具体价格指向管理平台 | 分钟降雨、雷达等是值得评估的能力；本次未取得可公开核实的长期免费额度 | 想强化“什么时候下雨”时再评估，不能承诺免费替换 |
| 高德天气 | 本次核实了天气 API 能力，未取得适用于当前分发方式的完整免费配额和商业许可结论 | 城市实况与短期预报，需 Web 服务 Key；官方提示以返回的 `reporttime` 判断更新时间 | 如果已有地图体系可复用；目前不优先为天气单独引入 |

来源：[W1]—[W9]。厂商宣传的“精准”“公里级”是产品能力描述，不等于已经证明在用户所在区县优于其他服务。

特别注意，**和风当前每日预报文档列出的新接口是 `/weather/v1/daily/{latitude}/{longitude}`，最多 10 天**，并拆分白天、夜间预报。旧教程中常见的其他接口版本、套餐名称和预报天数，不能不加核对就用于新设计。[W4] 如果从当前 16 天改用该接口，日期格的覆盖范围需要明确处理，不能把第 11—16 天伪装成同源预报。

Open-Meteo 的开放数据许可与免费托管接口的使用条件也要分开：数据采用 CC BY 4.0，并不自动意味着商业产品可以无限免费调用它的公共服务器。[W1]

## 哪一种接入方式适合桌面应用

### 无账户、无服务端

保留 Open-Meteo，优化缓存、过期提示和请求失败处理。这条路线对用户最省事，维护成本最低。适用前提是满足免费接口条件，且能够接受其网络与服务保障。

### 用户自己填写天气凭证

提供和风等来源选择，用户配置自己的账户信息。维护者不承担所有用户的调用费用，代价是设置门槛。凭证放在主进程管理，使用系统加密存储，日志脱敏；不要在界面、错误导出或渲染进程中暴露完整凭证。

### 应用提供统一天气服务

由应用服务端调用厂商，并按地区与时间缓存，同城用户共享结果。这条路线最有利于统一默认体验、控制调用量和保护应用的共享凭证，但会新增服务端运维、限流和费用管理。

**不要把维护者的共享 API Key 或 JWT 签名私钥打进 Electron 安装包。** 打包、混淆或放在主进程都不能让分发给用户的共享秘密不可提取。和风支持 JWT 与 API Key，推荐 JWT；这不等于在所有桌面客户端内放同一份私钥就是安全的。[W5]

一个说明量级的例子：假设服务端缓存 100 个城市，每 30 分钟分别请求一次当前天气和逐日预报，按 30 天计算：

```text
100 城市 × 48 次刷新/日 × 2 个接口 × 30 日 = 288,000 次/月
(288,000 - 50,000) × 0.0007 = 166.60 元/月
```

这是基于当前公开阶梯价的估算，不含其他服务请求，实际账单按厂商计费规则计算。逐日预报通常无需与当前天气一样频繁刷新，合理拆分后还能减少请求。

## 比更换接口更重要的设计

建议明确保存 `provider`、预报生成时间、抓取时间、有效时段和过期状态，让用户看得懂自己看到的是什么。

当前天气可先以 10—30 分钟为刷新候选，逐小时预报 30—60 分钟，逐日预报 1—6 小时；这些与和风官方缓存建议相符，最终仍应依接口时效和产品用途确定。[W6] 设备睡眠恢复、日期跨天、地区切换需要重新检查时效。重试应退避，多个窗口应合并相同请求，不能每个组件自行轮询。

日历日期格展示全天预报；工具栏展示当前天气。不能只因当前晴天，就抹掉今天下午的降雨风险。若当前天气与日预报来自不同来源，至少应在详情中说明。跨源补齐必须逐字段或逐日期保留来源信息，不能把混合结果统一标成“中国气象局”。

如果你最关心“哪个更准”，建议做一项限范围的真实评估：选取用户常用的若干地区，持续记录 2—4 周的数据，固定比较提前 24/48 小时的最高最低温和降水事件，同时记录访问成功率、响应时间与过期率。温度用绝对误差，降雨用命中、漏报和空报区分。**本次没有厂商账户与观测对照数据，因此没有把任何一家宣布为实测最准。**

## 每日宜忌：免费方案的关键差别

| 库或数据源 | 当前核实情况 | 适合用途 | 需要保留的边界 |
|---|---|---|---|
| `chinese-days` | 项目当前使用；农历、节气、节假日/调休；MIT | 保持现有日历行为 | 不能直接提供每日宜忌 |
| `lunar-javascript` | 1.7.7；MIT；无第三方依赖；提供日、时宜忌 | 快速接入本地黄历展示 | 宜忌是归纳得到的数据表，不能宣称逐条复原某部古籍 |
| `cnlunar-js` | 0.2.0；ESM；Node.js ≥14；MIT；Python `cnlunar` 的移植 | 需要追溯传统宜忌规则的产品 | 要核对移植一致性、支持年份、月界与时区 |
| `tyme4ts` | 6tail 的后续日历库；MIT；文档提供 `getRecommends()` / `getAvoids()` | 新项目或长期统一历法抽象 | 本次核实了文档，未运行其宜忌计算，也未确认其数据来源与旧库的差异 |
| 云端黄历 API | 不同服务的免费次数、鉴权、稳定性不统一 | 已采购其他聚合服务时顺带使用 | 对本地确定性功能增加网络依赖，通常不划算 |

### `lunar-javascript` 的真实数据来源

作者的每日宜忌文档明确说明：从 2345 日历采集十多年宜忌数据，研究规律后制作查找表，并提醒输出可能与其他地方不同。[A2] 因此应区分：**代码的 MIT 授权已经核实；上游采集数据的来源与再分发授权没有被本次研究独立确认。** 不能把“MIT 开源”写成对所有原始数据权利的完整保证，也不能把表格输出称为国家标准。

这个库的流派参数有精确定义：

- `sect=1`：以“节”交接的当天起算月，默认值。
- `sect=2`：以“节”交接的具体时刻起算月。

**这不是“农历月模式”和“公历月模式”的区别。** 对只显示一个日期的每日宜忌，可以先固定一种日级规则，避免同一个日期在不同时刻悄悄变化；具体选哪一种应在来源说明中可追溯。

返回 `['无']` 是该库的有效结果，不是接口失败。产品需要区分“无特别宜/忌”“不支持该日期”和“计算失败”。

### `cnlunar-js` 的取舍

上游 `cnlunar` 明确参考《钦定协纪辨方书》，采用神煞、月日关系及宜忌轻重规则；其 README 也承认没有完整翻译全部原书，部分理解仍可能需要校正。[A3] 因此，“有传统出处”比“输出绝对权威”更准确。

本次已分别核对上游与移植库的当前 LICENSE，均为 MIT。上游长篇 README 中仍保留旧的 GPL3.0 说明，与当前 LICENSE 不同；实际引入时应锁定版本并保存该版本的 LICENSE，避免混用历史说明。[A3][A4]

### 为什么不同万年历会互相矛盾

宜忌不仅取决于公历转农历。不同实现还可能采用不同的节月界定、年界、子时换日、神煞集合、规则优先级和词语映射。《协纪辨方书》卷十已有“宜忌等第表”“铺注条例”，要求比较轻重、决定取舍；不是把所有吉神的宜事项与所有凶神的忌事项简单并集。[A6]

所以，要追求的是**同一来源、同一规则、同一版本输出稳定且可解释**。如果与用户常用万年历不同，应能指出采用的规则，而不是在多个来源中挑一个看起来更吉利的结果。

## 推荐的产品落点

日历日期格只放简短的“宜 / 忌”摘要，完整条目在选中日期的详情中展开。宜忌可以是可关闭的文化信息显示项，保持现有便签、天气、调休行为清晰。

字段建议独立于现有农历字段，至少保存日期、宜、忌、提供者、算法版本、规则标识和是否支持该日期。计算放在主进程，按月或当前可见日期批量生成并缓存；无需联网，也无需引入 Python 运行环境。已有 `chinese-days` 继续负责调休等数据，两个库的农历和节气结果需要做交叉一致性检查。

文案采用“传统黄历参考”，详细页列明来源。不要用 AI 临时生成每日宜忌，也不要把传统“忌求医”等条目改造成阻止现实行动的提示。古籍条目可以作为文献内容保留，不能当作现代医疗、气象或风险判断依据。

如果之后增加梅花易数，建议独立为“起卦记录与研读”入口，不用它覆盖每日宜忌。它需要事件与起卦规则，单纯按日期生成一个卦只是某种固定规则的文化展示，不代表传统梅花所有占法。
