# 日常与深度排查模式的本地诊断设计

日期：2026-09-28。状态：基础双模式、源头许可、后台存储、跨窗口导出和界面控制已实现。本文保留最初代码审计及验收目标；当前行为见 [维护指南](../LOGGING_GUIDE.md)，已验证范围与未覆盖项见 [重构验收记录](../testing/logging-refactor-2026-09-28.md)。性能预算仍须按设备和场景验证，一次性下次启动及 profile 是后续可选项。

## 1. 设计结论与边界

采用两种用户可见模式：**日常模式**长期运行，**深度排查模式**由用户启动并自动到期。两种模式共用事件协议、关联 ID、隐私规则、后台写入器和导出能力，差异发生在采集源头，而不只是文件写入等级。

日志系统承担四种职责：记录重要事实、汇总运行指标、保留有限操作轨迹、按需取得更详细的性能证据。错误等级、数据用途、采集成本、保存目的地分别定义；不能把所有 `info` 当作日常日志，也不能把所有 `warn` 都当作故障。

继续本地保存和用户主动导出，不建设服务端遥测。保留“近一小时”和“全部保留日志”两个导出范围；“全部”仍受保留时间和空间上限约束。诊断不得修改业务结果、事务、输入行为、置底行为、材质或滚动算法。

本文中的容量、频率和性能数字都是**本项目的首版设计预算**，需要定向基准测试校准，不是企业通用标准或已经验证的性能保证。

## 4. 独立读库、页面摘要等较贵观察的策略

这类工作必须在调用前取得采集许可。只在 `writeLog` 中过滤，仍会执行查询、摘要和 DOM 访问，达不到降开销目标。

- 日常保留所有显式重要修改的最终结果。独立读回默认按 actionId 确定性抽取 1%，全应用最多每分钟 1 次；只验证被修改的字段/关系，避免无关附件/标签查询。未被选中不执行仅供诊断的前后查询或内容哈希。
- 深度模式默认针对便签修改与设置的已选轨迹执行独立验证。首次预算为每秒 5 个验证操作，全应用共享令牌；超额保留结果与 `verification=skipped-budget`，不排队补查成错误时点的“证据”。数据无变化、异常和读回失败分别表达。
- 在业务调用开始时决定采集票据及是否取 before，结束时使用同一票据。开关在操作中途变化时不能伪造缺失的 before，也不把 after 当历史状态；涉及同步读取/摘要的工作不可依赖 JavaScript 超时强制中断，只能在调用前限量，并在超时后停止后续额外观察。
- 独立核验必须注明观察时点和版本。异步操作期间同一对象已被另一操作修改时，无法排除竞争的比较记为 inconclusive，不能把较新的内容判定为本次保存失败；不为日志另开业务事务、延长锁或改变提交顺序。
- 读取结果优先做内存比较，仅输出 changedFields/mismatchedFields、长度、存在性、版本等。默认不把内容哈希持久化；SHA256 不是匿名化保证。需要长文本摘要时另设字节上限，超出记录 `skipped-size`。
- 页面日常采用数量/版本等现有数据，不额外构造 100 条便签数组；深度模式才启用有界列表摘要、诊断专用 nextTick/帧回调和结构计数。任何业务本来依赖的等待/校验不能被模式开关跳过。

代价必须明确：**日常模式不再保证为每次静默写入失败提供独立读回证明。** 抽查不等于全量验证，深度模式也不能恢复开启前未采集的正文或状态。需要更强的数据正确性保障时，应由业务事务/校验负责，不让诊断观察承担该职责。

## 5. 采集策略、关联与协议

新增共享策略表，为每个事件家族声明 `kind`（event/metric/trace）、默认目的地、优先级、字段白名单、采样/聚合方式、单条体积和成本等级。`level` 仅表达严重程度。登记新事件时必须说明它回答的诊断问题和替代证据，避免同一事实在多个层反复落盘。

源头 API 需要同时支持三类调用：轻量 `count/measure`、带懒构造 metadata 的事件、需要先申请预算的昂贵 `observe`。策略判断先于参数摘要、堆栈格式化、数据库读取、DOM 访问和 IPC 克隆。昂贵读取只能显式申请，不能藏在普通事件 getter 内。

日常计时优先放在 IPC、顶层查询、任务和图片工作队列等共用边界；嵌套 hydrate、逐项渲染、原生几何等细分计时按深度模式开启，避免“没有文件日志但每个函数仍不断分配计时对象”。应用版本/运行时等静态上下文缓存，窗口完整状态仅在变化、异常和深度检查点刷新，不再为每条 Renderer 信息重新调用多个窗口 getter。

主进程是模式状态的唯一权威，维护 `mode`、`policyVersion`、`policyEpoch`、`captureId`、起止时间与预算。Renderer/preload 缓存带到期时间的只读策略；启动握手和更新推送失败时回落日常模式，不能无限保留深度采集。授权与实际窗口身份仍在主进程检查，actionId 和 Renderer 自报 mode 不构成授权。

事件继续保留 sessionId、actionId、parentActionId、windowRole、PID、阶段/结果，并增加 producerId、producerSeq、单调时间、mode、policyEpoch 和 captureId。聚合记录携带采集区间、样本量、单位、采样策略及丢弃信息。不同进程单调时间不可直接相减；使用原有 actionId、各进程 timeOrigin 与主进程接收时间辅助对齐，并保留时钟跳变/暂停说明。

轨迹按整次 action 采样，不能随机丢掉中间某一阶段。失败或明显变慢时，提升缓冲区内同一 action 的近期记录；缓存里没有的字段仍标为未采集。合并刷新继续保留多个 causeActionIds，不归因给最后一个请求。模式切换中的在途操作保留原始策略代号，终态正常归属；不能等待全部业务完成才结束采集。

## 6. 近期轨迹和自动保存

日常采用**有容量和时间上限的内存缓冲区**保存关键轨迹：目标为最近 2 分钟，满时先覆盖最旧记录，所以高负载下实际可追溯时长可能短于 2 分钟。错误、关键业务结果和低频指标仍正常落盘。

Renderer 只缓冲紧凑白名单字段，活跃且有新增数据时日常每秒最多向主进程送一批，深度每 250 ms 最多一批；每批日常最多 32 条或 16 KiB，深度最多 64 条或 32 KiB。达到条数/体积上限只截断本批，不突破发送频率；积压按覆盖/合并规则处理。异常可走小型优先批次，但仍有限频；逐滚轮、逐帧不产生传输。批次在收到确认前计入在途容量，每个 producer 最多 2 个未确认批次，不能依靠 `send` 的返回值判断下游已接受。

自动保存只冻结已有近期轨迹和接下来 30 秒的**日常粒度**数据，用户可见模式仍为日常。建议首版触发条件：

- 未捕获异常、非正常进程退出、窗口 unresponsive、实际验证 mismatch。
- 前台且未跨休眠/隐藏边界时，10 秒内出现 3 次超过 250 ms 的主进程延迟，或一次超过 1 秒；页面输入/Long Task 采用对应阈值，长观察间隔不自动归因为卡顿。
- IPC 超过已有 2 秒 pending 门槛：按操作类别排除有预期长等待的对话框/文件导出，只为异常类别保存现场。超过某个毫秒数不是通用错误定义。

同类现场 60 秒冷却，最多 3 个/10 分钟，同一时间最多一个自动现场，重叠触发合并原因和 actionId。重复异常增加计数并关联已有现场；达到上限继续保存紧凑错误摘要。冻结现场的待写数据也计入现有信用额度，不另建无界副本。用户主动开启深度模式或导出不受自动触发次数限制，但仍受全局空间/传输预算限制。日志写入失败不触发更密集采集。

主进程已经接收的轨迹可用于 Renderer 崩溃现场；最后一个未送达批次可能丢失。主进程崩溃或断电会丢失尚未落盘的内存，现场必须标明缺口，不能承诺总有完整“事前录像”。

## 7. 模式切换与使用流程

应用启动默认日常。日志界面展示当前模式和采集状态，提供“开始深度排查”，默认 10 分钟；可停止或明确延长，单次最多 30 分钟。用户正常操作复现，再使用现有导出按钮。深度到期后已采集的数据继续按保留策略存在，不立即删除。

状态过程为：日常 → 准备采集 → 深度采集中 → 正在收尾 → 日常。准备阶段检查写入器是否可用、冻结近期轨迹、记录各窗口采集能力并广播策略；不等待较慢的完整系统快照才允许复现。缺失窗口确认记录为 partial，不显示成全窗口已开启。

到期同时使用绝对期限和本进程单调计时上限，任一达到即结束；休眠期间不延长额度，恢复先判断是否到期，再决定启用采集器。新建窗口读取当前策略；关闭窗口立即清理 timer、observer、rAF 和 transport。Renderer 本地到期可自行降级，主进程回收策略时同步确认。

改变采样频率时重建 CPU/原生计数基线。当前 `GAP_MS=15000` 同时用于观察中断和 CPU 样本有效期，不能直接沿用到日常 30 秒采样：必须拆开这两个阈值，CPU 最大有效间隔按采样频率设定（首版为 `max(15 秒, 2.5 × 资源采样周期)`）；明确休眠/模式切换仍直接重置，避免正常的 30 秒间隔被全部算成缺失。

若复现必须重启，提供独立的“下次启动采集”入口：只创建一次性、24 小时内有效的短租约，下一次启动消费后删除，采集仍只持续 10 分钟。租约只含时间、策略版本和能力选项，独立于业务数据库；不能把深度开关永久写进普通设置。此入口可在基础双模式验收后实现，避免先扩大首轮界面改动。

预算保护是内部健康状态，不增加第三种用户模式。磁盘不可写、下游拥堵或采集自身持续超预算时，深度模式提前结束/降级，并显示“采集不完整”和原因；错误记录及已有导出尽力保留。不会因采集失败阻止用户保存便签。

## 8. 写入、队列、查询与故障处理

首版选择专用 Node Worker 承担日志 JSON 编码、文件写入、轮转清理以及查询/导出解析。主进程只处理策略、授权、轻量白名单校验、聚合和必须由 Electron 主进程调用的 API。Worker 不访问业务 SQLite、DOM 或 Electron 窗口对象；这是隔离事件循环开销，不是保证主进程崩溃后 Worker 仍存活。

链路为：采集许可 → 本进程计数/紧凑记录 → 有界批次与确认 → 主进程路由/近期缓冲 → Worker 队列 → JSONL。优先级为严重错误/生命周期、关键结果、指标、详细轨迹。日志调用不等待文件写入；诊断排序依靠序列号与时间，不改变业务 await 顺序。

| 资源          | 首版预算                                                                 | 达到上限时                                                                                                                              |
| ------------- | ------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------- |
| 普通事件      | 编码后最多 8 KiB；错误含堆栈最多 32 KiB；聚合批次最多 64 KiB             | 源头限制深度 4、对象键 32、数组 32 项、字符串长度；记录省略数量。Worker 再检查编码上限，不能先无界 stringify                            |
| 近期轨迹内存  | 主进程 2 MiB；Renderer 每个 256 KiB，所有 Renderer 合计最多 2 MiB        | 按全局额度分配，覆盖最旧项并输出实际时间范围；不随便利贴数量无上限增长                                                                  |
| 运输/写入积压 | 应用合计 4 MiB 的受管 payload 信用额度，其中 512 KiB 保留给错误/控制事件 | 计算本地排队和已发送未确认数据；优先合并指标、丢旧轨迹、限流重复错误。结构化克隆/运行时内存另做实测，不能把 payload 上限当进程 RSS 上限 |
| 写入批次      | 正常每 1 秒或 64 KiB；严重错误请求优先刷新                               | 已有写入未完成时等待后台写入，不在主线程同步兜底；高优先级也受硬容量约束                                                                |
| 落盘文件      | 继续单卷 5 MiB，总预算 50 MiB                                            | 日常文件池 30 MiB/最多 14 天；现场和深度文件池 20 MiB/最多 7 天，按池清理最旧完整卷/现场，避免详细日志挤掉日常历史                      |
| 单次深度现场  | 最多 10 MiB                                                              | 达到即收尾恢复日常，记录容量终止原因；有界终态/manifest 预留空间包含在池预算内                                                          |
| 错误重复      | 首例立即保存，之后 30 秒一次重复摘要                                     | 保存 count/firstAt/lastAt/恢复状态；指纹缓存也必须有容量上限，不能丢计数或无限增长                                                      |
| 查询/导出     | 同时 1 个导出任务；查询分页最多 200 条，单页返回字节有上限               | Worker 逐块解析/让出执行，优先让新记录入队；取消后释放文件引用，避免多个导出扫描相互叠加                                                |

容量限制在写入时执行；文件轮转、日期变化和定时维护均走 Worker，不能等用户打开查看器才清理。文件池包含现场 manifest 和采集状态文件；临时文件、重试副本也计入额度。老版 `app-*.jsonl` 纳入日常池，保证旧记录仍能读，必要时按新额度清理。

Worker 启动失败/异常退出时只允许有上限重启（首版 60 秒内最多 1 次），未确认批次可按 eventId 重发，读取/导出可去重；不要宣称文件严格 exactly-once。磁盘满、权限失败、部分写入、丢失 Worker 确认均进入独立健康状态，退避重试，不递归调用普通 logger。禁止在重试时改写业务文件或移除业务权限。

启动前和 Worker 故障期间使用同一有界内存后备，最小错误可尽力转发现有 stderr；没有可用持久化时明确返回采集不可用。正常退出在 `before-quit` 发有截止时间的 flush 请求（首版最多 1 秒），不再依赖 `process.exit` 才启动异步工作。fatal/强制退出仅尽力提交小型记录并保留现有 Crashpad，不改变进程退出语义，也不为“保证最后一条”恢复主线程同步全量写盘。

写入确认只说明写入 API 已完成，不等于断电持久化；常态不每条 fsync。尾部半行、重复 eventId、截断文件必须可读并在导出中计数。

## 9. 导出必须说明证据完整性

保持近一小时/全部的含义，导出不隐式开启深度采集，也不依赖日志查看器当前筛选。点击导出时建立 requestId、截止时刻和当前 producer 清单：

1. 请求所有存活且支持日志桥的窗口冻结/提交截止时刻前的本地统计和近期轨迹，首次预算等待最多 1 秒；销毁、后台节流、无响应窗口分别记录状态，不阻塞其它窗口导出。完整冻结无法及时响应时保留实际批次区间及 cutoff 限制。
2. 主进程加入未满周期的统计、现场索引和 Worker flush 屏障。屏障只等待已接受的批次到截止序列，不等待持续新增记录，也不等待业务调用结束。
3. Worker 固定文件列表和字节偏移，再按区间流式读取；导出引用的文件在任务期间不被清理，新增写入与时间范围不会污染分页快照。若保留引用使磁盘额度无法满足，终止导出并说明原因，不能让普通写入无限增长。
4. 收集系统快照并标明其真实采集时间。快照中慢/不支持的单项有期限，失败不阻止已有记录导出；明确 Promise 超时不保证取消底层同步/native 工作，优先缓存和真正可取消的外部命令。
5. 写入完成标记和 manifest：模式时间线、策略版本、captureId、窗口能力/确认、实际保留范围、丢弃/截断/重复/解析错误数、采集暂停、退出不完整、写入器健康、观察指标语义。失败/取消输出明确 partial，不把半个文件报告为成功。

复用 JSONL 作为首版交付格式，导出头/尾扩充 manifest，事件 schemaVersion 升级而兼容读取旧记录。近期记录导出时保留原时间、序列号与 actionId，不把导出时间冒充事件发生时间。跨会话“近一小时”仍按实际事件时间筛选，后台统计区间跨越截止时刻时标记重叠范围，不能伪造精确分摊。

原生 `.dmp` 默认仅列索引，不自动塞入 JSONL 或上传。Crashpad 文件不属于上述 JSONL 的 50 MiB：单独保留最多 3 个完整转储、总量 100 MiB、最多 7 天，取最先达到的限制，在启动和后台维护时清理本应用旧转储并记录清理数量。转储由原生崩溃设施生成，崩溃瞬间不能承诺这一维护额度已生效；活动/尚未完整的文件不删除。性能 profile/trace 若后续实现，以独立文件及 manifest 引用交付，其字节计入深度现场池，单独说明敏感性和大小。

## 10. 隐私与可解释性

两种模式共用同样的内容边界。禁止正文、备注、键盘输入、DOM 文本、剪贴板、图片、凭据、响应正文进入常规诊断。静态操作名/控件 ID 优先于自由文本。绝对路径改为应用路径类别或脱敏片段，URL 去查询/片段并采用服务名，启动 argv 只保留允许的标志名称。异常 message/stack 和第三方 console 需要专门的有界脱敏，不能因为 scope=error 就绕过。

递归序列化不读取任意 getter，不遍历未经限制的对象图；未知对象以类型占位。有多个捕获入口时使用 errorId/指纹关联，保存一个主错误和关联来源，避免同一个异常在 Vue、console、webContents 层重复刷屏。首次错误与重复摘要都需要保留可解释的次数。

导出能回答“采集器没启用”“API 不支持”“采样未选中”“超预算省略”“窗口没响应”“记录确实未出现”的区别。统计的缺失值不能填 0，记录不全不能推断业务失败。环境采集不能改变硬件加速、sandbox、窗口原生行为来验证猜想。

原始设计审计阶段未运行应用测试。后续实施已增加定向单元、真实 Electron、ASAR 加载及合成基准；具体结果以重构验收记录为准。仍未运行全量回归、安装/升级及客户环境测试。异步退出丢失、降低读回覆盖、跨窗口截止一致性和观察扰动仍需结合 manifest 及实际硬件分析。
