# BR-03/04 固定候选内测验收章程

日期：2026-10-10。状态：章程已建立，综合运行与候选包验收尚未完成。既有局部结果只证明对应 attempt，不提前填入本章程的通过栏。

## 1. 目的与边界

目标是把当前重构后的 Windows 10/11 x64 单机、单人便签软件交付为可下载体验的1.4.0候选。内测通过且产物未变时，正式发布复用同一文件与校验和；有修正时仅重验受影响范围并记录新产物。用户负责分发；本轮不提交、推送、打标签、公开 Release 或发送群消息。当前用户要求先做其它产品修改，不生成安装包。

保持现有拖动、贴边运动算法。自然卡顿的客户机器根因继续按25采证，不把受控延迟、模型坐标或本机专项当客户根因。Apple 参考外观保留。

只把正常用户输入、应用现有后台任务、系统事件、实际 IO 失败和可解释的合理迟到列门槛。多个本应用窗口、保存中退出、提醒与模板同时运行是单人可达场景；无限 IPC 洪泛、没有产品入口的内部交错不作默认门槛。

## 2. 候选身份与运行顺序

1. 先完成28—31确认的失效测试、误通过 fixture、必要源码映射和 Qt 剪贴板隔离；保留原失败记录。静态审查、结果适配、运行通过各自记录。
2. 冻结源码、配置、版本、锁文件、原生输入和产物身份。记录完整工作区候选文件 SHA256、运行 Node/Electron/Qt/MSVC 版本、原生 ABI22；不能用 HEAD 一项代表当前 dirty 候选。
3. 基础设施、unit 与 app 构建串行。Vitest 可写缓存当前在 app 构建输入闭包中，不允许并行写缓存后跳过来源校验；Qt 或 native 未认证完整闭包时重建并记录工具链。
4. 用户明确内测与正式使用同一个 `1.4.0` 版本及正常安装包名，内测通过后发布同一验收产物，不新增beta渠道或发行身份。用户随后要求暂不生成安装包，等待其它产品修改；候选打包与包内验收暂停。后续恢复构建时遵守 `--publish never` 与34的安装隔离边界。
5. 使用包内真实 exe、native/Qt 组件和 ASAR Worker 重验启动、核心保存/重启、截图/贴图、诊断导出及退出。源树 GUI 成功不能代替包内成功。
6. 实际安装、升级、卸载使用同一正常1.4.0产物，在可恢复Windows VM或独立测试机器中进行，保留生产GUID等身份验证真实升级链。不为本次内测另建同机平行发行身份。缺环境就写未覆盖，不覆盖当前正式安装、资料或用户剪贴板。

发生新的源码修改后，仅重跑受影响项和必要依赖；在最终候选稳定时合并一次验收结果，不因每个小改动全量重跑。

## 4. 诊断开销的计量方法

使用同机同一资料规模、同样窗口/毛玻璃/层级、同样操作顺序和固定观测时间，比较日常与深度。至少记录端到端操作耗时、主/renderer CPU与内存、日志字节/记录量、真实运动collector启停及采样完整性。先预热，再交替顺序重复，保存每轮原始结果；注明后台负载与样本数量。

不得拿合成 logger 循环替代真实应用运动采集，不为得到全绿临时关闭 GPU，也不虚构“零开销”或未约定的预算。若存在明显退化、日志暴涨、采样空洞或导出漏尾批，先缩小到实际阶段并定位，必要修复按局部复核。弱机长期、自然拖动卡顿仍留给测试用户。

## 5. 门槛、缺环境和交付

资料损坏、不能启动、保存失败却提示成功、基本窗口无法使用、升级破坏资料、诊断导出不可用是阻塞项。测试本身失效或缺协议时先修测试，不能误归生产，也不能删保护获得通过。

本机目前单屏1920×1080。强制 Electron 缩放只能证明该条件下布局，不能证明真实混合 DPI/双屏。实际 Windows 10/11 差异、双屏/拔屏、不同刷新率/弱机和自然卡顿记录为测试用户任务，不能写本机已通过。

交付必须同时提供：候选安装/可运行包、SHA256、完整来源身份、实际结果/未覆盖清单、已知问题、恢复方式和普通用户可执行的反馈步骤。只有包内关键链路有效、阻塞项关闭后才可称候选可交付；仍缺生产安装环境时必须明确安装验收限制，不称正式1.4.0就绪。
