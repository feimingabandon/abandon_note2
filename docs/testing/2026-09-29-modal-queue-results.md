# 弹窗 FIFO 梳理与专项验证

## 原有问题

- `App.vue`、`MonthApp.vue` 分别使用多个显示布尔值，没有覆盖业务编辑器的统一互斥机制。
- 软件通知到达时可能叠在编辑器上；启动更新被其他须知挡住后，部分关闭分支没有继续显示更新。
- 恢复默认设置触发首次使用须知时，会清除更新、通知、报表等显示状态。

## 当前规则

- 同一 Renderer 内独立业务弹窗共用 FIFO，按进入队列的顺序展示。当前项保持席位直至退出动画完成，或组件实际卸载。
- 首次须知、软件通知/通知历史、更新、节假日提醒、报表、日志、独立标签管理等在请求源通过 `useModalRequest` 同步登记，控制器传给 `AppModalShell`，避免 Vue 子组件更新顺序替代实际请求顺序。
- 自定义壳接入：列表修改便签、月/周完整新建和修改便签、修改循环模板、壁纸裁剪。
- 尚未展示的弹窗不渲染内容、不抢焦点或背景模糊；取消或卸载清除席位，同一组件重复请求合并。关闭中重新打开保留原席位。
- 子弹层是例外：放弃编辑/删除/下载确认、编辑器标签管理、通知历史详情、图片预览继续服务当前操作，同时阻止后续独立弹窗启动。
- Toast、Windows 系统通知、日期/下拉面板、无蒙层预览和非模态工作区不占 FIFO。列表底部内嵌新建面板不是全屏模态，也不占 FIFO。
- 通知窗内多条通知仍使用原有的翻页/确认逻辑；队列单位是弹窗实例，不改变服务端通知排序。
- 队列为页面会话内存状态；重启或切换导致 Renderer 重载后，沿用原有设置和待确认通知重新读取流程，不持久化弹窗先后顺序。

## 审查发现与修复

- 交接时取消并立即重新请求，旧激活回调可能误开已取消的弹窗。加入请求代次校验，在延迟移除旧席位前使旧回调失效；已挂载的壳仍等待退出动画结束。
- 仅在壳中监听布尔属性，不能保证同一轮更新的实际发起顺序。将独立业务弹窗的登记移到请求源，壳只负责展示及关闭交接。
- 截图便签原先等待两次 DOM 更新就尝试导入，排队时表单未挂载会导致接收失败。现在先写入现有会话草稿存储，再确认接收；轮到展示后导入表单，失败可重试且避免重复附件。暂存失败则拒绝接收，保留截图端的后续操作机会。
- 截图背景入口原先直接挂载裁剪器，绕过壁纸设置已有的队列接入。截图背景入口现已登记同一 FIFO，并在取消或保存后释放席位与暂存图片。
