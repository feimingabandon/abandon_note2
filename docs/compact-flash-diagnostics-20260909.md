# Windows 灵动岛收起 / 展开闪烁诊断（2026-09-09）

## 修复实现：原生 ABI 13

- 开启毛玻璃时，在真实窗口隐藏之前，用同一 Composition 提交将普通背景交给起点外壳，
  并在可运行消息泵的准备阶段等待 DWM 提交，减少开始时露出桌面的空档。
  关闭毛玻璃时底色属于 Renderer，保留 Start 阶段接管，避免两层半透明底色叠加。
- 外壳动画开始后、普通 Visual 仍不可见时，将普通 Overlay 及其 Visual 提前同步到目标。
  成功收口只交换可见性；仅故障回滚的几何不一致路径重新同步位置和尺寸。
- 窗口 show 的毛玻璃恢复延到当前显示消息栈返回之后执行；同窗口合并重复请求，
  执行前重新检查窗口有效、可见且仍是活跃主窗口，避免重建后操作旧窗口。
- 保留真实失败降级。新增原生失败步骤、Win32 错误 / HRESULT、线程 ID 和父窗口可见性；
  `blur.visible-restore` 日志记录恢复耗时与实际结果。
- 共享 ABI 从 12 升为 13，使旧 DLL 不能被当作已修复的原生组件使用。

Win11 本机未暴露旧问题，不代表旧代码的提交顺序可靠。Win32 几何、Composition 属性和
实际屏幕呈现并非一个原子步骤；系统合成器、驱动及负载都会影响可见中间态。
目前没有相同硬件 / 驱动条件下的 Win10、Win11 对照，不能声称 Windows 版本是唯一原因。

### 闪烁证据与定位边界

- 视频 1920 × 1080，约 20.55 秒。以下时间按解码帧索引与报告帧率估算。
- 第一轮收起：第 119–120 帧（约 1.98–2.00 秒），背景已居中在 x=1141。
  第 121–122 帧（约 2.02–2.03 秒），192 像素宽的背景短暂出现在 x=997，
  恰好向左偏移 144 像素；第 123 帧（约 2.05 秒）恢复 x=1141，随后正文进入。
- 第一轮展开：第 193 帧已是完整背景；第 194–195 帧（约 3.23–3.25 秒）
  又出现原胶囊的小背景，第 196 帧小背景出现在主窗口左侧，第 197 帧才恢复完整背景。
- 开始阶段也有短暂背景空帧：首次收起约 1.68–1.78 秒、首次展开约 2.81–2.85 秒。
- 新日志的 10 次过渡均完成；交接后的 Electron bounds、原生 parentRect / overlayRect、
  Renderer screenX / screenY 及固定层布局均保持目标值，没有对应的几何回跳。
  因此日志“几何正确”与视频“显示错误”并存；问题已缩小到原生材质呈现交接。

代码对应 `native_blur/blur_engine.cpp` 的 `FinishShellOnSta` → `SyncAndShow`：
动画期间普通 Overlay 还在旧坐标、旧尺寸；收口才调用 `SetWindowPos`，随后
`UpdateVisualSize`，最后重新显示普通 Visual 并撤下外壳。视频中显示出的
“旧位置 / 旧尺寸 / 新尺寸”组合与这段路径吻合。可把该路径确定为重点整改位置，
但 Win32 返回值和 Composition commit 完成并不等同于实际 DWM 帧；尚不能仅凭
现有日志断言到底是哪一次提交或哪一个 Visual 被提前呈现。

整改应在外壳仍遮蔽时提前使普通 Overlay 的目标坐标和尺寸就绪，再做可见性交接；
开始阶段则要检查外壳实际呈现与真实窗口隐藏之间的空档。禁止只改居中坐标公式，
也不能只加固定 sleep 后把“本机没看到”当作完成。

### 启动毛玻璃失败：已确定失败入口，具体原生步骤待区分

- 14:57:43.995：原生初始化成功。
- 14:57:44.417：Renderer 就绪，主窗口 show。
- 14:57:44.962：`restoreBlurForVisibleWindow` 的恢复配置失败，code=9 / unknown_failure。
- 14:57:45.583：降级处理销毁原生资源并关闭开关；截图中的错误与此一致。
- 用户点击后能重新启用；之后的灵动岛日志中 `blurEnabled=true`。

这说明首次初始化后的 show 恢复配置阶段出错，而不是截图开关误报。
`ApplyConfigAndWait` 默认同步期限为 500 ms；show 到报错约 545 ms，时间与超时吻合。
但当前 code=9 同时覆盖 SendMessageTimeout、SetWindowPos、DwmFlush 等失败，
不能把“疑似同步等待超时”写成已证实的具体根因。尤其该调用在 Electron show
事件栈内同步等待 STA，需检查窗口显示消息处理和原生显示提交的时序。

后续原生日志应保留失败步骤、GetLastError / HRESULT、请求起止耗时、STA 当前步骤及
父窗口可见性，避免所有错误折叠为 unknown_failure；再验证将恢复工作移出 show
事件栈是否解决问题。不能仅隐藏错误提示或无条件打开 UI 开关。

本轮只分析日志、逐帧提取视频并更新报告，没有修改应用代码，没有运行单元或全量测试。
尚需针对上述原生交接和启动配置路径实施修复并在用户的 Windows 10 电脑验收。

## 本次增加的采样

没有修改窗口位置算法、动画时长、透明度恢复 / 外壳释放顺序或原生 DLL。

`compact-window.handoff-diagnostics`：

- `before-handoff`：恢复真实窗口透明度之前。
- `shell-released`：同步释放外壳并恢复输入之后。
- `content-enter-ready`、`transition-completed` / `transition-failed`。
- `tail-0/16/50/100/200`：过渡返回后，继续覆盖稳定态持久化和窗口运行配置恢复。
- 每点包括 Electron 窗口及内容区坐标、透明度、可见性，以及原生父窗口、普通材质层、
  动画外壳的矩形、可见状态、材质尺寸。Electron 使用 DIP，原生矩形使用物理像素。
- `elapsedMs` 是实际采样时刻；尾段名称表示请求延时，不能当作精确帧时间。
  `readMs` 记录采样自身耗时。不重复输出上一轮原生动画的 timing 明细。

`compact-window.renderer-diagnostics`：

- 增加 `screenX/screenY/outerWidth/outerHeight` 和 `readMs`。
- 内容进入及稳定尾段读取三个固定呈现层的窗口内矩形、透明度、visibility。
- 稳定态后继续采样 200 ms；一次最多 256 点，3 秒兜底超时，结束时一次 IPC 汇报。
- `stage` 事件表示收到状态；Vue 尚可能没有刷新 DOM，判断实际布局优先看后续 `raf`。
- 不读取便签正文、图片、HTML；IPC 端只保留固定字段。
- 新过渡替换旧采样、窗口关闭或组件卸载时清理采样。不会让动画等待尾段完成。

这些均是窗口 / 布局状态观察，不是 GPU 实际呈现帧。若几何完全稳定但仍能看到闪烁，
下一步需结合录屏或 Windows 合成器呈现跟踪，不能把状态成功当作视觉成功。

## 复现方式

使用本次 `dist-test-20260909-compact-diagnostics` 中的新 Windows 测试安装包。
版本号仍为 1.2.0，旧安装包不包含新采样。

1. 在出现问题的电脑上完全退出旧程序，再覆盖安装新包。
2. 先保持原有设置，收起 / 展开 3–5 轮，每次结束后停留约 1 秒。
3. 记录看到闪烁的大致时间，从软件日志页导出新的 JSONL。
4. 如方便，再分别开 / 关毛玻璃各复现两轮，并注明哪组闪烁；录屏可帮助区分闪的是内容还是背景。
