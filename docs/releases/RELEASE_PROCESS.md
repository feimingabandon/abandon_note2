# Windows 发布与失败调查

本产品仅发布 Windows 10/11 x64。日常验证仍遵守 AGENTS.md 的局部测试策略；候选发布使用工作流中固定的完整发布检查范围。

## 候选构建与发布

1. 固定待发布提交，确认 package.json 与 package-lock.json 版本一致，并等待该提交的普通 CI 成功。标签发布会再次检查该 SHA 最新的 CI，失败、未完成或缺少结果都拒绝晋升。
2. 对该提交手动运行 `Build Windows release candidates`。质量检查与 Windows 构建并行；同一桌面的真实窗口专项保持串行。
3. Windows 入口 `node scripts/run-electron-window-tests.cjs release-window-frame` 统一构建原生引擎、截图运行时和应用，执行原有全部窗口专项，并检查测试前后输入、已发现工具及输出指纹。打包直接消费本次输出，不再重复应用构建。
4. 执行真实包截图和冷重启验收。质量/Windows 证据收集器分别检查每个尝试的进程、业务、证据、清理及最终报告；任一失败、缺项、阻塞、不完整报告或构建漂移都拒绝生成候选证明。
5. 汇合两路成功证据，将提交、工作流 run/attempt、版本、目标平台、必需测试范围与三个构建附件的 SHA-256 绑定到 `release-candidate-proof`。原始测试和失败诊断另外保留 30 天。
6. 用户已授权正式发布后，创建指向该提交的正式标签。标签流程只复用同一仓库、同一 SHA 的最新成功手动候选，重新下载并验证证明与每个附件哈希，然后创建 Draft。找不到候选时仍可按完整范围构建；最新候选失败、未完成或通过重试覆盖失败时，禁止回退到旧成功候选。
7. 候选附件或证明过期、下载失败、哈希不符时立即停止并调查；不要静默换用其他安装包。候选过期后可重新生成一个可追溯的新候选。
8. 按用户确认的正文验收 Draft，公开后核对版本页、latest、匿名下载及校验和。工作流拒绝覆盖已公开 Release 的附件。安装/升级/卸载和实机 DPI/多显示器验收单独列明，不从构建或包内检查推断。

普通 CI 是变更范围验证，不能替代完整候选检查。跨运行复用的是已经验收的同一份安装包字节；没有开启原生构建缓存的未经证明复用。发布本身继续需要用户明确授权。

## 每次失败必须调查

失败后先保存证据，再复现和修改。不得把同一运行的失败结果改成成功；新复测使用新的证据目录。GitHub 附件包含 attempt 编号，重跑不覆盖先前失败附件。候选选择不会跨过最新失败选择更旧的成功记录。

每次失败在本次工作记录或 `docs/releases/investigations/` 中至少记录以下内容：

| 项目       | 必需内容                                                      |
| ---------- | ------------------------------------------------------------- |
| 身份       | 提交 SHA、run/attempt、测试 ID、原始证据目录或链接            |
| 现象       | 第一条错误、退出码/信号、超时阶段、业务断言与退出状态分别记录 |
| 已证实事实 | 错误栈、窗口文字、日志、源码调用链及可重现步骤                |
| 未证实假设 | 明确标注；时序相关、GPU、环境、其他实例等不能凭相关性归因     |
| 根因与分类 | 产品、测试前置、构建调度或运行环境；如何从证据得出结论        |
| 修复       | 修改什么、为何消除触发机制、是否改变原验收范围                |
| 复测       | 原失败用例、确定性回归、最终退出码、业务/退出/证据/清理结果   |
| 剩余问题   | 未查明原因、未覆盖场景和发布阻碍；不能用复测成功替代根因      |

原因尚未确认时标为未解决并继续调查，不宣称已修复。环境阻塞需要具体失败点和对照证据；业务断言前的启动失败既不是业务通过，也不能据此断言产品错误。

修正测试应等待真实就绪状态，例如窗口可见、动画结束、按钮可命中、截图 `captureReady`。不能单纯延长等待直到碰巧通过。对资源生命周期缺陷，应补“资源销毁后迟到回调”等确定性回归，不能只靠多次随机成功。

## 卡住时的证据

runner 在清理本次测试进程之前，从独立进程采集归属匹配的窗口、原生错误框文字和进程信息，并保留首次失败原因。外部诊断失败单独记录，不改写原始测试结论。诊断有时间和输出大小上限，不读取或结束其他软件及用户正在使用的长期实例。

证据收集不等于自动查明根因。发布负责人仍须读首次失败、完成上述调查记录，确认修复后才继续发布。后续绿色结果不自动豁免这一责任。

## 性能变化的验证边界

旧流程实测 Release 17分19秒，其中质量检查6分31秒与 Windows任务10分23秒串行。并行后的理论收益约6分半，实际受 runner排队、冷缓存及工具链影响；在新工作流真实运行前不承诺具体耗时。

此次先优化独立阶段并行、重复构建与候选包重复制作。单元测试多进程启动和依赖树散列仍保留原有校验，后续应单独测量后再优化，不以削弱失败检测换速度。
