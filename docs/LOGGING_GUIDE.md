# 日志系统维护与排查指南

2026-09-28：双模式日志已实现。此文描述当前行为；最初设计和验收目标见 [设计稿](research/2026-09-28-logging-modes-design.md)。本系统只在本地保存，由用户主动导出。

## 用户操作

设置 → 查看日志，默认显示“日常记录”。出现问题后，可直接导出近一小时；需要复现时，开启“深度排查（10 分钟）”，复现后停止并导出。可以延长，每次现场最多持续 30 分钟；到期、容量达到上限、写入器不可用或连续采集过慢时会恢复日常。重启后回到日常，不保存长期深度偏好。

两种导出都不受查看器筛选条件影响。“全部”指当前仍保留的文件。导出不会开启深度模式。

## 采集覆盖

| 观察边界                                 | 日常                                          | 深度                           |
| ---------------------------------------- | --------------------------------------------- | ------------------------------ |
| 生命周期、错误、崩溃、关键 IPC 结果      | 保存，重复错误合并                            | 相同                           |
| 一般操作过程、通知接收、刷新过程         | 主进程最多保留 2 分钟 / 2 MiB 近期轨迹        | 保存详细轨迹                   |
| 主进程、页面性能聚合                     | 30 秒；主进程保留 1 秒轻量时钟检查            | 5 秒                           |
| 滚轮/滚动/点击、Long Task                | 被动计数；每秒最多一次下一帧探针              | 交互期间及之后 1.5 秒观察 rAF  |
| DOM 结构数量、Vue 更新阶段、刷新后帧观察 | 关闭                                          | 开启；隐藏/卸载/退出深度时取消 |
| SQL、IPC、图片、后台任务已有操作的耗时   | 复用公共边界汇总；不记录逐项数据              | 增加嵌套归因和原生调用耗时     |
| 便签/设置的额外数据库读回                | actionId 确定性 1% 抽样，全应用每分钟最多一次 | 每秒最多 5 次                  |
| 原生贴边的诊断状态观察                   | 隐藏期间 2 秒                                 | 隐藏期间 250 ms                |
| 系统/GPU/显示器/ACL 快照                 | 导出时按需采集                                | 相同                           |

原生业务监控、窗口恢复、滚动算法不由诊断模式控制。读回跳过明确记录 `skipped-policy` / `skipped-budget`，不会称为已验证。重叠写入和超出哈希观察大小的内容标为 `inconclusive`，失败读回为 `unavailable`。内部比较可以使用哈希，落盘只保留长度和变化字段。

错误、读回不一致或明显卡顿可以保存近期轨迹和随后 30 秒现场，最多每 10 分钟 3 次、同一原因 60 秒冷却。不自动开启 profile、录屏或远程上传。下次启动一次性采集和 CPU/Chromium profile 属于设计中的后续可选项，当前没有启用。

## 新功能怎么接入

优先使用已有公共业务边界。普通 IPC 的失败和汇总耗时会自动被包装；数据库、图片和任务使用现有公共函数时复用其观察点，无须再复制日志。

新业务动作需要可读的操作名称、结果和 actionId 时，在 `src/shared/diagnostic-actions.js` 的通道表登记一次。preload 的请求上下文随同参数原子传输，主进程用 AsyncLocalStorage 保持并发隔离。不要用最近一次点击或全局 FIFO 推断操作归属。

只有新增状态机或需要解释“返回后究竟应用了什么”的特殊分支，才补一个有限事件。昂贵诊断必须在查库、遍历、哈希或读 DOM **之前**检查许可。额外同步工作可用 `measureSyncPerformance` 的已有类别及操作名；纯深度记录可带 `detail: true` 和懒 `metadata` 工厂，日常时工厂不会执行。关键错误不要标 `detail: true`。

每个新采集点在代码评审中说明：诊断问题、是否已有公共观察、所属模式、触发频率、最大字节/耗时、缺失语义、私密字段边界、直接相关测试。禁止为每个鼠标事件、动画帧或循环元素单独发送日志。先累计次数/耗时，再按周期提交。

## 写入与预算

`diagnostic-policy.js` 定义采集策略；`diagnostic-state.js` 管理短时租约和验证额度；`logger.js` 负责本地路由、近期轨迹和错误合并。两个 preload 复用 `diagnostic-transport.js` 源码，构建后仍各自为单文件，符合 sandbox 限制。

主进程/Worker 之间管理最多 3 MiB 排队与在途 payload，保留 512 KiB 高优先级额度；所有 preload 合计最多 1 MiB，主窗口最多 256 KiB，其余通常 32 KiB，额度不足时明确拒绝注册。额度包含未确认批次；不把这些上限当作进程 RSS 上限。超过运输吞吐时丢弃低优先级记录并计数，不阻塞业务。

Worker 执行 JSON 编码、异步文件写入、查询、导出和清理。普通批次最多 1 秒等待或约 64 KiB，严重错误请求及时提交。后台失败采用退避，60 秒内最多重启一次；未确认批次可重发一次，读取按事件 ID 有界去重，不承诺 exactly-once。没有主线程同步写盘兜底。

新事件 schemaVersion 为 3；单条普通记录 8 KiB、错误 32 KiB、聚合指标 64 KiB。遍历有节点、深度、键和数组上限，不调用任意 getter；正文、备注、二进制和凭据字段会被省略，路径与 URL 参数会被整理。旧 JSONL 继续可读，异常自由文本及历史文件不承诺绝对匿名。

日志分为日常池 30 MiB / 14 天、详细池 20 MiB / 7 天，每卷最多 5 MiB；单次详细现场上限 10 MiB。写入时轮转，定期后台维护。初始化目录失败不会永久缓存失败状态，目录或权限恢复后会重新尝试。

查询按事件时间合并两个池，时间相同按冻结文件序号和字节位置确定稳定顺序。由于近期轨迹回放也会使单个文件内部乱序，每页扫描固定快照，仅保留最多 201 个候选偏移，再读取当前页；返回最多 200 条 / 1 MiB。后续写入不进入已有分页快照。大容量搜索会消耗 Worker 的文件读取和解析时间，不在主线程排序全部记录。

同时仅允许一个导出。保存对话框等待期间或正在读取期间，如果保留额度要求删除已固定的文件，会使相关查询快照失效、中止相关导出并释放文件占用，让新日志继续写入。被中止的导出会显示明确错误并清理临时文件，不覆盖已有目标文件，也不会在稍后确认保存时重置中止状态。

Crashpad 不上传。Worker 维护本应用已完成且静置的转储，通常最多 3 个 / 100 MiB / 7 天；近期和 pending 转储不删除，崩溃瞬间和维护前可能暂时超过额度。JSONL 导出只列索引，不包含转储内容。

## 读导出文件

先看 `diagnostic-complete`：`exportFinished` 表示文件写出完成，`complete` 表示本次提交与解析未报告缺失。manifest 包含窗口能力/确认、截止时刻、策略时间线、模式/captureId、队列丢弃、写入错误、重复/坏行和保留文件偏移。`complete: false` 时仍可分析已有证据，但不能用“没有这条记录”认定事件没有发生。

所有存活窗口均有至多 1 秒的冻结/提交机会；未响应、不支持或已经丢失数据分别列出。便利贴关闭、主视图切换前，preload 最多等待 800 毫秒提交聚合和待发送记录；页面卸载另做一次尽力提交。只有主进程收到匹配的最终序列且没有报告丢弃，才确认页面结束提交完整；后续新记录会撤销该确认。强制销毁、崩溃或未确认提交均标为 `partial`，不阻止用户关闭窗口。

已结束页面保留最近 64 个状态，包括同一个窗口重新加载前的页面。更早状态只保留省略数量及其中不完整数量，并写入 `logging.producer-ended` 事件；省略不完整状态后也不能把本次会话标为完整。这些状态随导出 manifest 一起交付，不因窗口从存活列表消失而被忽略。

保存对话框打开前固定文件和偏移，快照租约为 2 分钟，过期后明确要求重新导出。导出补交的统计带 requestId，允许统计生成时间略晚于点击截止时刻，原始事件时间保持不变。时间区间重叠不进行虚假的精确分摊。

`returned` 只证明接口返回，`data-applied` 只证明 Vue 数据提交，rAF 频率不是实际呈现帧率，GPU 进程 CPU 不是 GPU 利用率。采集缺失、API 不可用、超预算和业务失败分别分析。

正常退出先收集各页面，页面提交与写入屏障各有 1 秒等待预算；窗口和业务资源清理完成后，最终异步写入另有 1 秒预算。上述诊断等待不包含原有草稿确认、远程会话结束或 Worker 终止耗时。启动失败也做有限提交。突然断电或进程强制终止仍可能丢失最后记录；写入 API 完成不代表每条都已 fsync。
