**Abandon Note：天气自动刷新与传统黄历设计方案**

评估日期：2026-09-28。本文保留最初评估依据；用户随后确认实施并要求便签列表也提供万年历。最终实现、已确认边界与测试记录见 [整合实现方案](2026-09-28-weather-and-almanac-implementation.md)。以下“候选”“预计”“未执行”等措辞描述当时的评估状态，不代表当前实现状态。

本方案依据当前工作区、Open-Meteo 官方文档、《钦定协纪辨方书》卷十及候选库源码。天气以用户明确的“免费、免 Key、尽量简单接入”为约束，取代 2026-09-24 调研中优先评估和风天气的建议。全文提出的是完整目标行为，不区分所谓第一版、第二版。

**一、推荐决策**

- 天气保留 Open-Meteo；主窗口正常展开显示且天气已开启时，每 30 分钟检查并更新到期数据；隐藏、最小化、灵动岛和系统休眠期间暂停，恢复显示时检查时效。
- 当前天气与全天预报分别表达；自动更新只影响天气信息，不重载便签或播放整页刷新动画。
- 宜忌采用本地固定规则。文献依据优先选择《钦定协纪辨方书》体系，工程候选选择 `cnlunar-js`，通过日期边界、移植一致性及规则样例验证后锁定版本。
- 保留现有农历、节气和调休系统。宜忌主要出现在所选日期的详情中，不给每个日期格增加常驻的两行文字。
- 文案使用“传统黄历”，来源写清实际库和所参考文献，不宣称“官方统一宜忌”或与所有万年历相同。

**二、当前代码与设计需要解决的问题**

| 当前情况 | 对设计的影响 |
|---|---|
| `src/main/index.js` 启动刷新，并在每天 09:00 后安排一次天气更新 | 持续运行时不能跟进午间或下午的天气变化 |
| `weather-service.js` 普通读取只要有缓存就返回，并标记 `stale: false` | 必须按时间和数据内容判断时效，不能把“有缓存”等同于“新鲜” |
| 中国地区并发请求 CMA 与自动模型，两个请求都使用 Open-Meteo 域名 | 一次刷新目前包含两次 HTTP 请求；这是模型补齐，不是独立天气供应商回退 |
| IPC 已合并部分自动请求，手动路径等待后另行调用服务 | 自动、手动、恢复窗口和地区切换应进入同一请求协调逻辑，避免竞态 |
| 天气存在于月周工具栏、日期格、侧栏和普通列表的便签卡片 | 调度必须由主进程统一管理，不能只依附月周组件 |
| 今天的日预报天气码被当前天气码替代 | 当前天气与全天预报需要独立字段和展示语义，避免此刻晴天掩盖全天降雨提示 |
| 日历已用 `chinese-days 1.5.9`，有独立节假日数据服务 | 增加宜忌不要求替换现有农历或放假调休流程 |
| 日历允许浏览 1900—2100 年，候选库基础表从 1901 年开始 | 宜忌需单独声明实际支持范围，不能缩小整个日历的范围或越界循环计算 |

**三、天气刷新策略**

建议固定采用 30 分钟，不增加需要用户理解模型更新周期的设置。理由是：天气展示属于便签的辅助信息，30 分钟能明显改善上午数据滞留到下午的问题；5 分钟轮询并不能把数值预报变成现场观测；60 分钟则会增加可见信息的滞后。

Open-Meteo 的当前天气使用 15 分钟粒度的模型数据，CMA 模型标注每 6 小时一轮；数据粒度、模型发布频率和客户端请求频率是三件不同的事。不同时间请求可得到不同当前时段的数据，同一轮预报内也可能存在晴转雨。30 分钟策略改善信息及时性，不承诺提高模型预测精度。[W1]

| 场景 | 目标行为 |
|---|---|
| 启动且主窗口正常显示 | 先显示有效缓存；无缓存或距成功获取已满 30 分钟时后台更新，缓存未到期则复用 |
| 主窗口正常展开显示 | 到期后更新；普通列表、月、周视图共享调度。列表极简模式隐藏天气卡片时仍沿用主窗口策略，避免新增复杂的组件可见性协议 |
| 窗口没有焦点、置底或被别的窗口覆盖 | 不以失焦作为暂停条件；桌面便签可能仍然可见。不额外探测其他应用的遮挡情况 |
| 最小化、隐藏到托盘、灵动岛、锁屏或休眠 | 暂停定时请求，保留缓存 |
| 恢复正常显示、解锁或唤醒 | 重新判断时效；到期只补一次，不补发休眠期间的每个周期 |
| 启用天气、切换地区 | 缓存必须属于当前地区及模型策略；无匹配缓存则立即获取，到期缓存先显示再更新 |
| 关闭天气 | 停止请求和重试；在途结果不得重新显示天气或覆盖关闭后的状态 |
| 手动更新 | 有同地区在途请求则复用；距上次网络尝试不足 5 分钟则提示稍后更新；成功获取后重算下次自动到期时间 |
| 跨日 | 立即重新匹配日期与“今天”，不把昨日当前天气套到今天；无当天有效信息或已到期则更新，已有新鲜当天信息不额外请求 |
| 断网后网络恢复 | 到期且窗口正常显示时补一次，受统一限流与退避约束；网络在线事件只作为提示，不能证明服务可达 |

正常调度可附加 0—60 秒随机延迟，避免很多客户端在固定整点同时请求；启动无数据、地区切换和用户手动操作不增加这种延迟。30 分钟是刷新目标，实际到达时间还受网络和上游服务限制。

移除“每天 09:00”独立网络刷新路径，由同一个调度器覆盖全部触发原因。复用项目现有调度服务；检查到期不代表每次检查都访问网络。

**四、天气请求合并、失败与缓存规则**

1. 按地区标识、坐标、时区、模型策略形成请求键。自动、手动、首次读取和恢复窗口共享同一在途任务。月周与列表读取缓存不得各自创建轮询。
2. 使用设置修订号或请求代次验证返回结果；A 地区切到 B 再切回 A 时，旧 A 请求也不能仅因地区相同而被误认为新结果。天气关闭、视图重建及销毁均需处理在途任务。
3. 分别记录最近尝试时间、最近成功时间、当前数据时刻和下次重试时间。返回旧缓存不算成功，不推进成功时间；磁盘写入失败也不应被误记成网络失败并立即重复请求。
4. 网络异常或 5xx 依次在 5、15、30、60 分钟后重试，之后最大间隔 60 分钟，成功后恢复正常周期。只在允许自动请求的窗口状态下执行；暂停后保留退避状态。
5. 429 遵守 `Retry-After`，所有入口共用限制；没有该字段则使用退避。其他明确的参数/鉴权类 4xx 停止周期性重试，保留可解释错误，不按分钟无限重试。
6. 手动更新可在距上次尝试至少 5 分钟后提前于普通网络错误的自动退避重试，但不能绕过服务端 `Retry-After`。连点、显示/隐藏窗口和重复联网事件都不能重置限流。
7. 保留 12 秒请求超时。中国双模型分别判断成功与失败；一个成功时显示有效数据，并保留实际来源及另一个模型失败的信息。部分成功不得触发每个调度 tick 都重试缺失模型。
8. 对首次失败且无缓存的情况显示简短状态，不生成 0° 等占位天气；有缓存时保留内容并标明旧数据。自动失败静默更新状态，手动失败才反馈操作结果。
9. 系统时钟回拨、缓存时间位于未来、时区变更及跨日都需要重新校验。界面的数据年龄随本地时钟更新，不能必须等到下一次网络请求才发现已过期。

缓存状态建议采用以下产品阈值。这些是本应用的展示策略，不是气象精度保证：

| 条件 | 展示 |
|---|---|
| 成功数据未满 30 分钟 | 正常显示；详情提供获取时间 |
| 满 30 分钟，正在更新 | 保留旧内容平滑替换，不闪空、不显示整页遮罩 |
| 本次更新失败 | 明确显示“更新失败，显示 HH:mm 数据”；不能一律称为“离线”，失败也可能是限流或服务器异常 |
| 当前天气的数据时刻或获取时间已超过 2 小时 | 显示“数据较旧”；缺少可验证的数据时刻时不能宣称实时实况 |
| 当前天气超过 6 小时，或不属于天气地区的当前日期 | 从紧凑的“当前天气”位置隐藏，详情可保留最近一次记录与时间 |
| 全天预报距获取超过 6 小时 | 标记旧预报；超过 24 小时不再在日期格、便签卡片显示，详情可保留并提示需要更新 |
| 目标日期不在预报覆盖内 | 不显示天气；不能用邻日补齐或把历史预报说成历史实测 |

`fetchedAt` 应记录有效响应收到的时间；`current.time` 是当前字段对应的天气时刻。Open-Meteo 的 `generationtime_ms` 是接口生成响应的耗时，不能当成模型发布时间。接口未提供的发布时间保持缺省，不能自行推导。

**五、天气显示与请求量**

建议将当前信息和全天信息明确分开：

- 月周工具栏显示当前天气，例如“晴 24°”；完整说明中包含“当前天气，12:30 更新”。今天的日期详情同时显示当前气温和今日最高最低温。
- 日期格、便签卡片及日期详情的全天部分使用日预报，显示“今日预报：阵雨，18°～26°，降水概率 70%”这类信息。日天气码只是全天概括，不由此编造“下午三点下雨”。
- 如果当前天气无效但全天预报有效，工具栏可显示带明确“今日预报”语义的摘要，不把全天温度区间冒充当前气温。
- 当前与全天变化只对天气区域做轻量过渡；不清空或重载便签，不触发太极按钮及整月刷新动画。更新设置页原有“启动时、每天 09:00 或手动更新”的说明。
- 这是对现有工具栏语义的明确调整，实施时同步修改 `docs/UI_DESIGN_STANDARD.md` 对工具栏天气的条款；复用现有主题、浮层和动效令牌。

刷新频率与模型选择分开处理：本方案保留现有中国地区 CMA＋自动补齐，便于判断刷新改动本身的效果。每个模型请求仍在同一个接口中包含当前天气与日预报，无需为每一天单独请求。

| 持续显示时间 | 常规刷新次数，约值 | 中国地区现有策略的 HTTP 请求数，约值 |
|---|---:|---:|
| 8 小时 | 16 | 32 |
| 24 小时 | 48 | 96 |

表中不含首次无缓存、手动刷新、切换地区和失败重试；其他地区当前为每次一个模型请求。保留 16 天预报会超过官方“两周”的基本计数范围，因此 HTTP 请求数不能直接等同于服务配额计数。Open-Meteo 免费托管服务限非商业用途，并有 600 次/分钟、5,000 次/小时、10,000 次/日、300,000 次/月等限制；公共出口可能聚合多个客户端，不能把单机估算当成所有用户总量的保证。[W2]

无需增加用户 Key，也无需为了刷新而新增应用后端。该方案未验证中国各地的模型准确度，不能据此宣传“天气更精准”。

**六、“公认的宜忌”应该怎样理解**

需要区分历法规范、传统文献和软件输出：

| 层次 | 可以采用的依据 | 不应由此推出的结论 |
|---|---|---|
| 农历编算 | GB/T 33661-2017《农历的编算和颁行》，官方题录目前标为现行；后续验收结合可靠历表 | 某个开源库已经通过标准符合性认证，或该标准规定了每日嫁娶开市宜忌 |
| 传统择日文献 | 《钦定协纪辨方书》是清代官方编纂、具有代表性的择日文献，可作为明确规则依据 | 历朝历代及所有通书流派都只有同一套取舍 |
| 软件实现 | 对选定文献、月份口径、神煞集合和冲突规则进行确定性实现 | “MIT 开源”或“很多软件使用”就代表宜忌唯一正确 |

本次没有找到足以把某套每日宜忌称为全国统一标准的依据。国家标准官方题录已经核实，但本次没有取得标准全文逐条验收，也没有对任何候选库作符合性认证。[A1]

推荐目标是：**来源可信、规则固定、结果可复现、差异可解释。** 不以多个商业黄历的多数票拼出一份结果，也不根据用户便签内容动态生成“宜工作”“忌拖延”。

《协纪辨方书》卷十明确记载“先依用事次第察其所宜忌之日”，再“较量其吉凶之轻重，以定去取”，并包含宜忌等第与铺注条例。这支持采用完整取舍流程，而不是简单汇总神煞或遇到冲突一律判忌。[A2]

**七、宜忌引擎与统一口径**

推荐以 `cnlunar-js` 作为待验收的实现候选：2026-09-28 读取的仓库 `package.json` 为 0.2.0，当前 LICENSE 为 MIT。它移植自 Python `cnlunar`，规则具有《协纪辨方书》的注释与取舍结构。实际接入必须核对发布包与所审查提交，锁定精确版本，保存许可证和本项目适配差异，不能浮动跟随 master。[A3][A4]

`lunar-javascript` 的接入更方便，但作者说明其宜忌表来自对 2345 历史数据规律的归纳；这不如当前候选直接满足“规则出处与解释”的优先级，因此不作为主方案，也不在运行时作为无提示的备用宜忌源。[A5]

建议明确采用如下日级口径。这是本项目公开的默认选择，不声称全部流派都认可：

| 项目 | 建议口径 |
|---|---|
| 查询对象 | 用户选中的公历日期 `YYYY-MM-DD`；不读取此刻时间来改变该日期的结果 |
| 历法时区 | 中国历法按 UTC+8；不跟随天气城市变化。海外电脑查询同一个日期键仍得到同一份结果 |
| 年界 | 农历年及候选库年干支采用春节口径，显式指定 `year8Char='year'` |
| 月界 | 宜忌月建采用候选库维护的默认节月口径，显式指定 `godType='8char'`，按交节日期处理，不冒称精确交节时刻 |
| 年神规则 | 显式固定候选库默认的 `yeargod='duty'`，记录到规则标识，不依赖以后上游默认参数不变 |
| 日界 | 应用在日期切换到次日时展示次日结果；同一日期在 23:00 后仍返回原日期结果 |
| 带时刻的库适配 | 日级计算固定采用该日期的 12:00 参考时刻，作为技术取值约定记录在规则版本中；不将此约定称为古籍统一规定。上线前核验所有涉及时刻的分支 |
| 流派设置 | 产品不增加多个无法向普通用户解释的规则开关；详细来源页明确既定口径 |
| 输出范围 | 只提供通用每日黄历；个人八字择日、时辰宜忌、梅花起卦不混入每日结果 |

候选源码已经暴露出三个必须先验证的问题：

1. 库读取 `Date.getHours()`，并在 23 点分支调整日干支；直接传入当前时刻会使同一日期结果变化。
2. 它读取宿主本地年月日，部分逻辑使用 `Date` 差值。必须通过适配层保证按日期字段和中国历法计算，覆盖海外时区与夏令时。仅把一个带 `+08:00` 的字符串传给 `Date` 并不足以解决本地 getter 问题；不修改 Electron 全局时区来影响其他业务。
3. 农历年份查表使用取模索引，超出表范围可能静默回绕；2100 年末还有查下一年节气的问题。必须在入口判断真实支持边界，不接受“没有抛错所以支持该年”。

如果适配需要维护少量源码差异，应集中于引擎适配层，保留上游归属与规则测试；不得在界面组件中补丁式改变吉凶结论。若一致性验证失败，则保留可复现样例修正或更换候选，不以另一个库自动补几天形成混合规则。

**八、宜忌计算与数据表达**

计算流程固定为：日期与干支信息 → 建除、神煞等规则匹配 → 候选宜忌事项 → 宜忌等第及铺注例外处理 → 最终条目。

最终结果使用提供者已经完成取舍的输出。应用层仅做结构校验、同义词说明、确定性展示排序和同侧重复项清理，不自行决定“吉神多于凶神就算吉日”，也不再加一层“忌优先”的冲突算法。发现最终同一事项仍同时出现在宜忌两侧时，记录为规则差异并人工核查，不能悄悄删除其中一侧以伪装正确。

建议在独立 `almanac-service` 与共享规则模块中返回以下信息：

- 日期、状态、最终宜项与忌项；状态区分正常、超出范围、计算失败。
- 特殊结论，如“诸事不宜”“诸事不忌”“余事勿取”，与普通事项数组分开表示。原文保留，具体含义以所采用规则为准。
- 建除、日干支、相关神煞作为详情信息；不能仅凭列出的神煞声称已经解释了每一条宜忌。
- 实际提供者、精确库版本、规则版本、时区和日期取值口径。缓存键包含日期及规则版本。

“无特别宜项”“无特别忌项”“超出支持范围”“计算失败”是不同状态。不能把返回的“无”解释为报错，也不能把“余事勿取”改成“没有限制”。

术语采用原词加简短释义，例如“嫁娶（结婚）”“入宅（迁入新居）”“移徙（迁居）”。释义只解释古词，不把“纳财”重新包装成投资建议。首页摘要按固定、公开的显示顺序优先呈现常见生活事项；完整条目保留原词和全部内容。

**九、界面建议**

增加持久化的“传统黄历”开关，默认关闭；开关是月周共享的日历设置，与天气开关独立。用户开启后：

- 选中日期的现有侧栏中，在日期基本信息与便签列表之间显示紧凑黄历区域。天气区域继续保留自身位置和独立显隐。
- 摘要固定两行：宜、忌各显示最多 3 项；省略时明确提供“查看全部”，不让用户误以为摘要就是完整列表。没有常见项时从剩余原始条目补齐；不根据吉凶营销价值筛选。
- “查看全部”使用可滚动的详情浮层，展示完整宜忌、术语说明、日干支、建除与来源。标题始终带所选日期，避免快速切换时误读。
- 日期格不增加常驻宜忌文字，不挤压便签横条、休班徽标和快速新建区。侧栏关闭时可通过日期右键“查看黄历”显式打开对应日期侧栏并定位到黄历区域；普通点击日期仍沿用原有选择行为。
- 普通便签卡片和列表极简模式不添加宜忌小组件；日历信息集中在日期详情，避免与此前精简卡片的方向冲突。
- 宜忌使用明确文字标签及现有语义色，只强调标签，不把整日涂成红色或绿色，也不新增凶吉评分、百分比或“官方认证”标章。
- 切换日期时保持外壳稳定，结果按日期请求代次替换。旧结果不能在新日期标题下停留；尚未就绪时显示短加载状态，不阻塞便签。
- 展开、收起复用现有浮层和动效；支持键盘、Escape、焦点恢复和窄窗口边界。完整条目只在详情内部滚动。

用户可见来源示例：“传统黄历参考 · 规则参考《钦定协纪辨方书》”。详细来源中补充实际实现与版本，并简短说明“不同通书口径可能有差异”。这不是原书逐条全文认证，不使用“原版官方黄历”等称呼。

**十、年份、离线与更新**

不需要保存未来几十年每天的字符串，也不依赖每日 API。根据内置历法数据和规则按需计算所选日期，并使用有容量上限的内存缓存即可；不要在主进程启动时计算全部年份。

候选库说明中的基础表为 1901—2100 年，但实际可用范围必须检查首年春节前、末年冬至后等边界后确定。现有主日历的 1900—2100 年浏览范围保留；无可靠宜忌的日期在详情标为“该日期暂不支持”，农历、便签和其他日期操作继续可用。

宜忌规则修订随应用更新，规则版本变化使派生缓存失效，并在变更说明中记录会影响结果的修正。农历、节气按内置数据或算法工作；官方放假调休继续通过当前节假日服务更新，不能由宜忌库推算多年后的调休安排。

**十一、实现边界与局部验收方案**

天气预计涉及 `src/main/services/weather-service.js`、`src/main/ipc/register-weather-ipc.js`、主进程调度接线、`src/shared/weather-rules.js`，以及已有天气展示/设置组件。可以新增专用天气刷新策略模块，把时钟和窗口状态作为可注入参数，避免把复杂状态逻辑继续堆进 `index.js`。

黄历预计新增独立主进程服务与日期规则适配模块，接入现有日历 IPC；只按需查询所选日期，先完成便签数据加载，避免一次计算 42 天的所有择日规则阻塞月历。设置需同步覆盖 schema、application-settings 与 Renderer 可写白名单，不创建第二套设置持久化。新组件复用现有材质，不修改便签数据模型。
