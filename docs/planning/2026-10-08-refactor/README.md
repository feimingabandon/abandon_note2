## 3. 每阶段指导文档必须包含的内容

每份指导文档均需包括：

1. 当前源码基线、读取范围、已确认事实和证据不足的边界。
2. 阶段目标、允许改动的范围、应保留的产品行为。
3. 可独立追踪的问题编号、对应功能和具体文件。
4. 每项为什么修改、如何修改、先后顺序及依赖。
5. 需要同步调整的调用方、IPC、存储、原生 ABI、构建、测试、文档和 CI。
6. 需要保留的旧行为、兼容与数据迁移约束。
7. 对应的局部验证、必要平台验证、验收条件和未覆盖环境。
8. 回退方法，特别是数据、文件、原生产物和已有用户改动的保护。
9. 实施检查表、阻塞项及尚待核验的问题。
10. 真实实施时的状态和证据位置；不得预填“通过”。

## 4. 统一改动条目模板

以下模板用于后续三个阶段的改动项；不要求为每个小函数建立繁重流程。

| 字段 | 要求 |
|---|---|
| 编号 | 测试 `T-xxx`、解耦 `D-xxx`、审查 `R-xxx`，编号稳定 |
| 状态 | 待实施／实施中／已验证／阻塞／取消；当前方案条目均为待实施 |
| 问题与证据 | 说明现状、触发条件、源码或结果依据；推测单列 |
| 目标行为 | 使用可观察结果说明完成后的行为 |
| 文件范围 | 列出修改文件、拟新增文件、受影响调用方 |
| 修改步骤 | 写到实施者能按步骤操作；不只写“优化”“补测试” |
| 前置依赖 | 引用条目编号，区分必要依赖和可并行事项 |
| 验证 | 指定测试文件、场景、构建和平台条件 |
| 完成条件 | 能逐项判断的验收标准 |
| 回退 | 代码、测试、配置、产物和数据分别如何恢复 |
| 未覆盖风险 | 记录真实环境或规则尚不明确的部分 |
| 实际结果 | 实施时填写改动范围、命令、退出码、断言、证据和版本 |

## 5. 阶段之间如何衔接

- S2 应引用 S1 的测试契约与风险编号，确认重构前后哪些行为必须一致。测试迁移随业务职责迁移进行，不为新目录结构重复生成同一批测试。
- S3 同时审查生产代码与验证方法，区分产品缺陷、测试缺陷、实现质量问题和环境阻塞；不能用测试通过替代源码审查。
- S4 将每个 D/R 条目映射到相关 T 条目和验收场景。两个条目修改同一状态所有权或同一执行入口时，先合并方案，再实施。
- S5 先建立可恢复基线与必要保护，再做小批次修改。若重构顺序影响测试入口建设，在 S4 调整依赖顺序并说明原因。
- 新发现的范围变化先写回对应指导文档；保留原编号和决策原因，避免聊天结论与文档互相矛盾。
